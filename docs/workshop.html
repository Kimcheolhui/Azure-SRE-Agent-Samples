경고, 고객 영향, 원인의 차이

경고는 설정한 관측값이 조건을 벗어났다는 신호입니다. 경고만으로 장애 원인이나 고객 영향 범위를 알 수는 없습니다. 먼저 영향을 받는 API, 결제 수단, 실행 환경, 인스턴스, 발생 시간을 확인합니다. 전체 평균이 정상이어도 카드 요청만 느릴 수 있으므로 요청을 구분해 조회해야 합니다.

0-2. AKS와 컨테이너 배포

AKS는 Standard control-plane tier로 생성합니다. 노드3대와 ACR Standard를 기본으로 사용하며 SRE Agent는 별도로 만듭니다. AKS가 관리하는 VM·디스크·네트워크는 별도 node resource group에 생성됩니다.

기존 node pool의 VM 크기는 같은 이름의 Bicep 재배포로 변경할 수 없습니다. 다른 크기의 pool이 이미 생성됐다면 새 v6 pool로 이전하거나 새 이름의 실습 클러스터를 사용합니다. 생성 실패로 일부 리소스만 남은 경우에도 AKS와 node pool의 실제 상태를 먼저 확인합니다.

Container Insights의 identity 관련 배포 오류

AKS의 omsagent 응답에 enabled/config만 있고 identity가 없는 경우가 있습니다. 이 템플릿은 별도 addon identity가 항상 있다는 가정으로 DCR 역할을 만들지 않습니다. 관리 ID 인증 addon과 DCR/association을 사용하며, 실제 수집은 ama-logs와 KubePodInventory/ContainerLogV2에서 확인합니다. identity를 다른 신원으로 임의 대체하지 않습니다.

0-3-4. 초기 조사 대상과 실행 설정

첨부 화면과 같은 빠른 시작 / 전체 설정에는 Azure 리소스와 로그 카드가 따로 있습니다. Azure 리소스에서 RG를 Reader 수준으로 추가하면 Agent 실행 UAMI에 Reader·Log Analytics Reader·Monitoring Reader 등의 역할이 RG scope에 할당됩니다. 같은 RG에 있는 LAW와 App Insights는 이 역할을 상속합니다. 이는 리소스 이름을 입력하는 것만으로 생기는 권한이 아니라, 설정자가 역할 할당 권한을 가지고 추가 절차를 성공시켰을 때의 결과입니다.

로그 카드도 권한을 할당합니다. Azure Log Analytics/Application Insights 연결을 저장하면 해당 관리 ID에 필요한 Log Analytics Reader와 Monitoring Reader가 자동 할당됩니다. 단순 원본 선택만 하는 UI가 아닙니다. 같은 RG를 Azure 리소스에서도 이미 연결했다면 권한 효과는 겹칠 수 있지만, 원본을 명시적으로 등록하는 설정은 별도로 남습니다. 저장 시 표시되는 역할/scope와 성공 여부를 확인합니다.

화면의 로그 ‘권장’ 표시를 권한 오류로 보지는 않습니다. 기본 Azure 로그 조회는 접근 권한과 실제 데이터가 있으면 별도 외부 커넥터 없이도 가능합니다. 다만 원본을 명확하게 지정하기 위해 이번 설정에서는 다음 단계의 로그 카드도 구성합니다.

  1. 새 Agent → 초기 설정 / Settings → PermissionsAzure 조사 대상으로 rg-payment-kch01x7만 추가하고 permission level을 Reader로 지정합니다. 구독 전체와 MC_... node RG를 일괄 추가하지 않습니다. 추가 역할 할당에는 해당 scope의 Owner 또는 User Access Administrator 권한이 필요합니다. PIM 사용 중이면 먼저 역할을 활성화합니다.
  2. Reader 수준에서도 로그/모니터링 Reader와 subscription 범위의 Monitoring Contributor가 할당될 수 있습니다. Monitoring Contributor는 경고 상태 관리용이므로 “모든 호출이 읽기만” 권한이라고 해석하지 않습니다. 역할 확인은 워크로드 RG / Subscription → Access control (IAM) → Role assignments에서 실제 Agent 실행 identity로 확인합니다.
  3. Agent → Settings → Basicsfallback mode를 Review로 유지합니다. response plan/task/HTTP Trigger를 나중에 만들면 각 설정에서도 Review를 확인합니다. Agent 기본값 하나가 모든 자동화를 통제한다고 가정하지 않습니다.
  4. Agent → Settings → Agent consumption활성 AAU 한도는 5,000 AAU를 이번 구성의 초기값으로 지정합니다. 이는 지나치게 작은 한도로 조사가 중단되는 것을 피하기 위한 월 active-flow 상한이며, 선결제 금액이나 항상 비용까지 포함한 전체 청구서 상한이 아닙니다. 현재 입력 가능한 범위와 비용 승인은 확인합니다.
  5. 초기 Code/Knowledge/Incident platform/Scheduled tasks 설정은 건너뛰고 Azure 읽기 조사만 확인합니다. 코드 연결은 Lab 7에서 Samples 저장소 전체를 대상으로 진행합니다.

0-3-5. Agent 실행 신원 확인

  1. Agent → Settings → PermissionsAzure 실행에 사용하는 user-assigned managed identity(UAMI)의 리소스 이름/ID를 확인합니다. 생성 시 생긴 system-assigned ID, AKS의 id-aks-payment-..., kubelet identity와 구분합니다.

  2. Log Analytics Workspace를 선택하고 Next로 이동합니다. 자신의 구독/워크로드 RG에서 law-aks-payment-kch01x7을 지정합니다. 연결 화면이 이름을 요구하면 logs-payments-kch01x7처럼 원본을 구분할 이름을 입력합니다.

  4. Next → review → Add connector로 저장합니다. 저장 과정에서 필요한 로그/모니터링 Reader 역할도 자동 할당됩니다. 권한 할당 오류가 있으면 우회하지 말고 해당 scope의 설정자 권한/PIM과 선택한 identity를 확인합니다. Test/Validate가 제공되면 실제 결과를 확인합니다.
  5. 추가 로그 원본이 필요하면 로그 +에서 Application Insights를 선택하고 appi-aks-payment-kch01x7을 연결합니다. core Azure 목록에는 Azure Data Explorer도 있지만 이번에는 만들지 않습니다. picker/세부 필드는 제품 버전에 따라 달라질 수 있으므로 해당 공급자가 실제 노출되는지 확인합니다. 여러 원본은 별도 연결로 추가합니다.
  6. 리소스 ID 필드는 해당 리소스의 Properties → Resource ID에서 복사합니다. LAW의 workspace/customer ID, App Insights app ID와 Azure resource ID는 다른 값입니다. 필드가 요구하는 종류를 맞추며 실제 ID는 문서/Git에 저장하지 않습니다.
  7. 저장 후 로그 카드의 연결 목록/표시와 아래 query를 모두 확인합니다. 연결 표시만으로 데이터 조회가 성공했다고 보지 않습니다.

0-4. 자동 할당된 AKS 조회 권한 확인

기본 흐름은 권한 추가가 아니라 자동 할당 확인입니다. SRE Agent에서 AKS가 있는 RG를 Reader 권한 수준으로 연결하면 리소스 종류에 맞는 AKS 역할도 자동 할당됩니다. 필요한 역할이 이미 상속돼 있으면 추가 명령을 실행하지 않습니다.

여기서 일반 Azure Reader 역할은 Azure 리소스 정보를 읽는 하나의 역할입니다. SRE Agent의 Reader 권한 수준은 그 역할에 로그·모니터링과 리소스별 읽기 역할을 함께 할당하는 설정입니다. 두 의미를 혼동하지 않습니다.

3-2. SRE Agent의 Azure Monitor 경고 연결과 진단 범위

경고 수집은 RG만의 범위가 아닙니다. 9-2. 정책을 넓은 Allow 없이 구성

9-3. Stop Hook으로 완료 근거 검사

AAU 비용과 작업별 사용량

AAU는 always-on과 active-flow로 나뉩니다. 일반 과금에서 Agent 하나를 30일 유지하면 4 × 24 × 30 = 2,880 AAU의 기본 비용이 발생합니다. primary와 Stopped standby를 함께 유지하면 5,760 AAU입니다. 평가 기간 면제와 현재 계약 단가는 별도 확인이 필요합니다.

active-flow는 input/output/cache read/cache write 토큰 수에 각 모델 요율을 적용한 합계입니다. 입력에는 prompt뿐 아니라 tool 결과와 대화 맥락도 포함됩니다. 승인 대기 시간 자체와 모델 처리 사용량은 구분합니다. AKS, 로그, Grafana, 네트워크와 외부 서비스 요금은 AAU에 포함되지 않습니다.

  1. Agent → Settings → Agent consumption날짜와 작업 종류 filter를 선택하고 실행한 thread의 AAU를 확인합니다.
  2. 현재 filter로 CSV를 export해 화면과 같은 기간/thread가 포함되는지 확인합니다. filter를 바꾸면 export 범위도 바뀝니다.
  3. Portal → Cost Management → Cost analysis실습 RG별로 AKS/로그/네트워크 등의 비용을 확인합니다. active AAU 한도는 전체 Azure 청구서의 상한이 아닙니다.

생성 권한, 리전, 모델과 감사

  1. Portal → Subscriptions → 실습 구독 → Resource providersMicrosoft.App 등록 상태를 확인합니다. 등록 변경에는 구독 관리자의 권한과 승인이 필요합니다.
  2. 생성 위치의 Owner 또는 Contributor + User Access Administrator, 각 조사 scope의 역할 할당 권한, PIM 활성 상태를 확인합니다. 설정자 권한과 Agent 관리 ID의 장기 접근 권한은 별개입니다.
  3. Agent → Settings현재 region/model provider를 확인합니다. 기존 Agent의 region은 변경할 수 없으며 다른 리전으로 옮기려면 새 Agent가 필요합니다. 모델 변경 전에는 비용과 데이터 처리 위치를 확인합니다.
  4. Agent → Monitor → LogsAgent 자체 Application Insights에서 customEvents를 조회합니다. 워크로드 telemetry와 Agent 감사 로그의 권한/보존을 구분합니다.

기능을 함께 사용할 때의 확인 사항

경고 규칙은 이상을 탐지하고 response plan은 조사할 사건과 담당 Agent를 선택합니다. 동적 임계값은 학습 조건을 충족해야 하므로 설정 직후의 탐지를 보장하지 않습니다. HTTP Trigger와 경고 scanner가 같은 사건을 중복 접수하지 않도록 확인합니다.

Grafana 정의를 읽는 권한과 실제 data source query 권한은 다를 수 있습니다. 운영 지식은 현재 상태의 근거를 대신하지 않으며 GitHub 코드는 실제 배포 SHA와 대조합니다. 읽기·변경·외부 전달은 각 실행 신원과 정책, 승인을 따릅니다.

예약 작업과 보고서는 실행 이력, 조회 시각과 설정 버전을 확인합니다. 사설 조회는 DNS가 실제 PE 주소를 반환하고 HTTP 요청이 성공하는지 검증합니다. DR 전환은 primary의 호출·자동화를 격리한 뒤 standby를 검증하고 한 Agent에만 실행을 활성화합니다.

샘플 장애 재현과 복구 확인

bash scripts/scenario.sh "$RG" "$CLUSTER" dependency-slow
node scripts/traffic.mjs "$APP_URL" 20 dependency-slow
# 실제 데이터 조회와 Review 승인을 거쳐 복구
bash scripts/scenario.sh "$RG" "$CLUSTER" healthy
node scripts/traffic.mjs "$APP_URL" 20 healthy
  1. 전용 실습 리소스 또는 로컬에서 장애 하나를 다시 만듭니다. 앞선 Lab을 참고해 필요한 명령과 조회 원본을 선택합니다.
  2. 대상/UTC/경쟁 가설을 정해 Agent를 조사시킵니다. 수동 KQL/HTTP 측정 근거를 모으고 Agent 결론과 대조합니다. 즉석 계산 파일은 입력 행/단위/출처를 검증합니다.
  3. 변경 대상/identity/RBAC/mode/approval를 직접 확인하고 승인된 최소 조치만 수행합니다. tool이 없으면 수동 실행을 명시합니다.
  4. 복구 뒤 node scripts/traffic.mjs "$APP_URL" 20 healthy를 실행합니다. 양쪽 count=20, failures=0, p95≤1,000ms와 복구 이후 telemetry를 기록합니다. p95를 못 맞추면 미회복으로 남기고 회선/앱 근거를 더 확인합니다.
  5. 다음 사람에게 넘길 1페이지 incident report와 재사용할 검증된 지식만 작성합니다. 마지막으로 scheduled tasks/triggers/report refresh를 중지합니다.

로컬 실행이면 APP_URL=http://localhost:8080을 사용합니다. 로컬 HTTP/console 결과는 Azure Monitor/RBAC/Portal을 검증한 결과가 아닙니다. 실제 구성하지 않은 외부 기능은 검증 여부를 별도로 구분합니다.

모든 실습 종료 시 반드시 진행 · 삭제는 직접 확인 후 실행

  2. Agent → Settings / Usage → 사용량, 스레드 상세Lab별 사용량을 기록합니다. Portal → Cost Management → Cost analysis → Resource group 필터Agent RG, 워크로드 RG, Grafana/네트워크 RG를 각각 확인합니다. 비용 반영에는 지연이 있습니다.
  3. RCA, 쿼리 결과, 승인 기록, 복구 전후 지표, 구성 export를 저장합니다. 로그/보고서의 민감 정보를 제거합니다. secrets 없이도 재구성할 수 있는 리소스 이름과 권한 목록을 남깁니다.
  4. Portal → Resource groups → 실습 RG → Overview삭제할 리소스 목록과 태그를 직접 확인합니다. 공유 RG이면 전체 삭제를 하지 말고 자신이 만든 리소스만 선택합니다.
  5. 다음 명령은 확인 후 수동 실행합니다. --yes를 넣지 않아 CLI 확인 절차를 유지합니다.
    az group show --name "$RG" --query '{name:name,tags:tags}' -o json
az resource list --resource-group "$RG" --query '[].{name:name,type:type}' -o table
az group delete --name "$RG"

az group show --name "$AGENT_RG" --query '{name:name,tags:tags}' -o json
az resource list --resource-group "$AGENT_RG" --query '[].{name:name,type:type}' -o table
az group delete --name "$AGENT_RG"

  6. GitHub connector/App 권한과 Key Vault 접근 역할, 로컬 MCP 설정, 워크샵용 action group을 정리합니다. GitHub App을 uninstall/delete할 때 다른 서비스가 쓰는 App인지 확인합니다. 남아 있는 AKS plan과 SRE Agent가 없는지 Portal에서 재확인합니다.
