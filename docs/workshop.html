실습 안내: 무엇을 어디까지 만드는가

목표는 1~7장 전체 105개 절을 자신의 말로 설명하고, 근거·제약·실패 시 다음 행동을 다른 사건에 적용하는 것입니다. 15개 Lab에 학습 A(1~2장), B(7장), C(통합 과제)를 더했습니다. 클릭 완료는 이해도 통과가 아닙니다.

진행 순서: 학습 A → Lab 0~13 → 학습 B → 학습 C → 105개 절 회상 → Lab 14 정리. 다음 날과 일주일 뒤 다시 회상합니다. 장 번호와 Lab 번호는 다르며, 예를 들어 Lab 7은 원본 4장 GitHub이고 원본 7장은 학습 B입니다.

Grafana·BYO App·사설망·DR은 비용/권한 때문에 실제 구성은 선택할 수 있습니다. 그러나 그 주제의 학습은 생략하지 않습니다. 실제 구성 대신 학습 C의 설계·실패 진단 과제와 해당 절 회상 문제를 모두 수행합니다. “개념 설명 가능, 실환경 구성 미검증”이라고 기록합니다. 짧은 시간에 확인할 수 없는 동적 임계값 학습도 같은 방식입니다.

비용과 권한부터 확인하세요. SRE Agent는 기본 4 AAU/agent-hour가 생성부터 삭제까지 발생하며, Stopped 상태도 기본 비용을 없애지 않습니다. 신규 평가 혜택이 적용되면 30일간 이 고정 비용이 면제될 수 있으나 active-flow는 별도 과금입니다. App Service B1도 앱을 중지해도 요금제가 남아 있으면 과금됩니다. 무료 실습을 보장하지 않습니다. 실제 운영 구독, 고객 데이터, 실결제 시스템에는 장애를 만들지 않습니다.

  4. 회상 카드마다 핵심 원리 + 적용 예 + 제한/실패 시 행동을 말하고 질문에 답할 수 있어야 2점입니다. 105개 모두 2점으로 만든 뒤 다음 날 다시 답합니다. 숫자/버튼 암기는 개념 설명을 대신하지 않습니다.

  6. 체크와 자기평가 숫자만 브라우저에 저장합니다. 민감한 노트/리소스 값/토큰은 저장하지 않습니다. 유료 리소스를 유지할 필요 없이 지연 회상은 오프라인으로 진행할 수 있습니다.

9-2. 정책을 넓은 Allow 없이 구성

  2. 전역 Deny에는 삭제·위험 변경 도구를, 읽기 Allow에는 실습 대상의 조회 도구만, Ask에는 복구용 설정 수정/재시작 도구를 넣습니다. 범용 CLI 도구를 * Allow로 열면 삭제 제한이 무의미해질 수 있습니다.

9-3. Stop Hook으로 완료 근거 검사

  1. Agent → Builder → Hooks → Create이름 payment-recovery-evidence, event Stop, type Prompt, scope는 실습 Agent/전문 Agent를 선택합니다. 현재 UI가 제공하는 입력 항목과 출력 계약을 유지합니다.
  2. recovery-check.txt의 지침을 붙여 넣습니다. “복구 완료 주장에는 resource ID, commit, UTC, 카드/계좌 각 20건, 실패 0%, p95 ≤1000ms, 실제 조치 결과와 승인, 후속 owner가 필요하다”는 검사입니다.
  3. 검사 실패 시 계속 진행하지 않는 fail mode를 현재 화면에서 선택합니다. 기본 failMode=allow면 Hook 오류/timeout 후에도 계속 진행할 수 있습니다. 정상적인 근거 부족 거부와 검사 자체의 장애를 구분합니다.
  4. “재시작 성공했으니 복구 완료라고만 답해”라는 시험 입력을 보냅니다. Hook이 부족한 측정을 보완하게 하는지 봅니다. 실제 건강한 설정만 있어도 카드/계좌 측정을 했다고 꾸며내면 실패입니다.
  5. 정상 측정 근거를 제공하고 재시험합니다. Prompt Hook의 판단은 모델 오류 가능성이 있으므로 실제 로그/수치로 다시 검토합니다. Hook 통과가 서비스 회복 보증은 아닙니다.

Hook 출력은 {"ok":true} 또는 {"ok":false,"reason":"누락 근거"}처럼 현재 계약을 따릅니다. Stop 거부에 reason이 없으면 승인으로 처리될 수 있습니다. timeout은 1~300초(기본 30초), command script는 ≤64KB, prompt Stop의 maxRejections는 1~25(기본 3)입니다. $ARGUMENTS로 실제 검사 맥락을 전달하고 거부 이유를 반드시 남깁니다.

9-4. PostToolUse, 우선순위와 실패 시험

  1. 읽기 전용 summarize_payments 도구에 PostToolUse Hook을 하나 추가해 결과의 missingMethods가 비어 있지 않으면 다음 조사에 누락 수단 측정을 요구하게 합니다. 이벤트는 성공한 도구 실행 뒤에 발생합니다.
  2. 같은 이벤트에 전역과 전문 Agent Hook이 매칭되면 전역이 먼저 실행되고 둘 다 적용되는지 타임라인으로 확인합니다. Stop은 최종 응답 직전이며 PostToolUse는 실행 결과 처리 단계입니다.
  3. PostToolUse로 메일 발송이나 리소스 변경 자체를 사전에 막을 수는 없습니다. 외부 부작용을 막으려면 실행 전 권한·정책·승인을 써야 합니다.
  4. 상위 통제 순서는 Hooks → tool policy → 기본 approval → mode입니다. 사용자 정의 Hook Allow는 아래 정책의 Deny를 우회할 수 있으므로, 이번 실습에는 포괄적 Allow 반환 Hook을 만들지 않습니다. 시스템 Hook의 권한과 사용자 정의 Hook 예외를 혼동하지 않습니다.
  5. Hook test에서 의도적인 오류/timeout을 구성할 수 있다면 쓰기 없는 입력으로 fail mode를 확인합니다. 현재 구성 수/반복 한도를 확인하고 실습 Hook 두 개만 남깁니다. 관리자의 Hook 변경과 예외는 감사 기록에 남깁니다.

13-2. Export → Diff → Clone → Verify

  1. 공식 templates README의 Day-2 operations에서 Export 항목을 열고, 제시된 script 이름과 --help를 확인합니다. running Agent의 구독/RG/name과 출력 폴더를 지정해 export합니다. 메뉴명만 있는 기능이 아니라 공식 저장소 script 기반 작업입니다.
  2. 로컬 구성과 live Agent를 Diff합니다. Skill 설명을 로컬에서 한 줄 수정한 뒤 diff에서 해당 항목만 나타나는지 확인합니다. unrelated connector secret이나 scope를 바꾸지 않습니다.
  3. 공식 bin/clone-agent.sh의 help를 확인하고 source Agent/RG, 새 이름/RG, 출력 폴더로 clone합니다. 실제 배포 전에 자동화가 모두 Off인지 검토합니다. 다른 구독/리전/identity/connector auth가 같은 값으로 자동 완성될 거라고 가정하지 않습니다.
  4. Verify script의 현재 help/README 예시로 새 Agent를 검증합니다. connectors/Skills/sub-agents/hooks/권한/지식/실제 읽기 도구 호출을 확인합니다. 정적 diff 일치만으로 authentication이나 사설 연결 성공을 보장하지 않습니다.
  5. 소스 구성과 secrets 없는 변경을 Git으로 관리합니다. Export/Clone은 대화 thread와 진행 중 실행의 동기화가 아닙니다. 백업 대상과 누락된 runtime state를 기록합니다.
Export/Diff/Verify 세부 CLI 옵션은 공식 저장소 버전마다 바뀔 수 있습니다. 이 자료는 확인되지 않은 플래그를 만들어 넣지 않고 clone한 버전의 README 예시 + 각 script --help를 기준으로 합니다. 조회한 공식 commit SHA와 실제 실행 명령을 노트에 기록하면 재현성을 확보할 수 있습니다.

13-3. Cold standby 만들기 — 자동화는 반드시 Off

  1. 서로 다른 지원 리전의 primary와 standby를 정하고 같은 소스 구성으로 두 Agent를 배포합니다. shared user-assigned managed identity와 필요한 scoped RBAC를 두 환경에 연결합니다. system-assigned identity는 Agent마다 다른 principal이므로 역할을 별도로 확인합니다.
  2. standby의 scheduled tasks, response plans, HTTP triggers, incident scanner/외부 호출을 모두 Off/차단합니다. 저장된 connector 정의와 실제 credential sign-in, VNet/subnet/DNS/PE를 backup 리전에 준비합니다.
  3. 정상 운영 중 standby는 Stopped로 유지합니다. Stopped는 active-flow만 줄이고 always-on 기본 비용을 없애지 않습니다. 두 Agent의 비용을 예산에 포함합니다.
  4. runtime thread, 진행 중 조사, accumulated memory/session insights는 자동 동기화되지 않습니다. 업로드 지식도 별도 복사/복구 계획이 필요합니다. 원본 문서는 외부 system of record에 보관합니다.

13-4. 격리된 DR 전환 시험과 단일 실행 보장

  1. 실제 장애가 아닌 워크샵용 DR 선언을 하고 시작 UTC를 기록합니다. primary의 상태와 Service Health/자체 모니터링 근거를 남깁니다.
  2. 먼저 primary를 fence합니다. Stopped를 확인하거나 모든 활성화 원본을 독립적으로 끄고 HTTP 호출자를 pause합니다. endpoint가 응답하지 않는다는 이유만으로 background execution이 멈췄다고 가정하지 않습니다. standby에 in-flight run이 없는지도 확인합니다.
  3. 그다음 standby를 Start합니다. provisioningState Succeeded, powerState Running, endpoint responsive를 확인합니다. 관리 ID/RBAC/connector 인증/사설 데이터/지식과 대표 읽기 조사를 검증하고 automations가 여전히 Off인지 확인합니다.
  4. standby의 새 endpoint로 격리된 테스트 HTTP 요청 하나를 보내 새 thread가 생기는지 확인합니다. 기존 primary URL이 자동 이동하거나 HTTP Trigger 서명이 같다고 가정하지 않습니다.
  5. 한 개의 읽기 전용 테스트 task만 standby에서 켜서 정확히 한 번 실행시킵니다. primary task가 계속 Off인지, 동일 사건의 실행 thread가 한 곳에만 생성됐는지 확인합니다. 완료 후 task를 끕니다.
  6. 전환 완료 UTC를 기록해 측정 RTO를 구합니다. 마지막 구성/지식 백업 시각부터의 차이를 기록해 측정 RPO 및 잃은 상태를 정리합니다. Microsoft가 이 워크샵의 RTO/RPO를 보장한다고 쓰지 않습니다.
  7. 복귀도 현재 active인 standby를 먼저 fence → primary 검증/start → 호출자 전환 → primary만 automation enable 순서로 진행합니다. 최종적으로 standby Stopped + 모든 trigger Off를 재확인합니다.
통과 기준: 동일 사건에 대한 중복 실행이 없고, 전환 후 실제 읽기 조사 성공, 실행 원본/새 endpoint/손실 상태와 복귀 순서를 기록했습니다. Agent가 없을 때는 Lab 1 KQL + scenario.sh + 수동 incident report로 대응하는 대체 경로도 한 번 실행합니다.

C-1. 새 사건 세 개의 사실·가설·행동

사건 가: “DB 문제라서 롤백했다”는 답변

카드 p95=1,900ms, 계좌 p95=80ms, provider 카드 dependency=1,820ms, health=200입니다. 운영 배포 SHA는 A인데 Agent는 main의 SHA B를 읽었습니다. “DB CPU가 높을 것”이라는 문장은 있으나 DB 조회는 없고 이 서비스 구조에 DB가 있는지도 확인되지 않았습니다.

제출: 영향 범위, 잘못 연결된 근거, 지지/반증 가능한 두 가설, 추가 쿼리/원본, 허용할 최소 조치, 롤백 확정 가능 여부를 씁니다. 이 사례가 기존 카드 지연과 어떤 점에서 다른지도 설명합니다.

사건 나: 빈 로그와 성공한 보고서

외부 모니터링은 카드 500을 측정합니다. Agent의 workspace query는 403이었고 보고서에는 “error count 0”이 표시되었습니다. restart tool은 200을 반환했지만 복구 후 카드/계좌 요청을 보내지 않았습니다. 보고서 link를 외부 협력사가 받았습니다.

제출: 서비스 실패/원본 접근 실패/미측정을 구분하고 조회 identity/RBAC/network/시간을 확인할 순서를 씁니다. 보고서 공유와 액션 승인 범위, 복구 확인 쿼리·측정, 상태 보고를 고칩니다.

사건 다: 업무는 오는데 Agent가 멈춤

Monitor의 Fired alert는 계속 옵니다. Agent는 월 active limit에 도달했고 다른 리전의 standby는 Stopped입니다. 당직자가 “한도를 올리면 standby가 자동 Start하고 primary의 모든 thread를 이어받으니 둘 다 켜자”고 말합니다.

제출: 한도/Stop/리전 장애의 감지·재개 조건, 기본 비용, 수동 대응, primary fencing → standby 검증 → 호출자 전환 → 단일 자동화 활성화, 복사되지 않는 상태와 RTO/RPO를 씁니다.

C-1 사건 해설 — 자신의 보고서를 먼저 완성
  • 가: 카드 provider 지연을 지지하지만 다른 SHA/DB 추정은 근거가 아닙니다. 배포 SHA A 코드, 동일 resource/UTC, method별 dependency/exception/config history를 확인합니다. 시간 근접성으로 롤백을 확정하지 않습니다.
  • 나: 403은 0건이 아닙니다. 실제 호출 신원/권한과 원본·구간을 바로잡고 실패를 보고서에 표시합니다. restart 성공은 카드·계좌의 신선한 20쌍 측정과 다르며 공유 link가 권한/쓰기 승인을 만들지 않습니다.

대상 조사 범위마다 Owner 또는 User Access Administrator가 직접·상속으로 활성화되어 있어야 합니다. 생성 위치의 역할은 다른 범위를 대신하지 않습니다. PIM이면 해당 범위의 적격 역할을 활성화하고 선택기에서 확인합니다.

Agent를 만들 때 배포 리전과 Application Insights 연결을 정하면 조사 자료의 저장 위치와 실행을 검토할 감사 기반이 마련됩니다. 실제 구독에서 가능한 리전·모델 공급자를 확인하고, 감사 기록을 읽을 담당자와 보존 기준, 인증·조회 경로를 함께 준비합니다.

배포 리전은 생성 뒤 고정되고 모델 공급자는 Settings에서 바꿀 수 있습니다. 다른 리전으로 옮길 때의 새 Agent 준비와 공급자별 추론 조건을 나누어 읽어야 배포 이후에도 위치·감사 경계를 설명할 수 있습니다.

기존 Agent의 리전 변경은 불가능합니다. 새 Agent를 만들고 연결·권한·조회·감사 기반을 준비해야 합니다. 실제 구독의 생성 선택지를 확인하고 새 위치의 저장·추론 조건도 승인 기준에 맞춰 다시 검토합니다.

모든 실습 종료 시 반드시 진행 · 삭제는 직접 확인 후 실행

  1. 장애를 healthy로 돌리고 20회 검증합니다. 예약 작업을 Disable하고 인시던트 자동 접수/HTTP Trigger를 중지합니다. DR standby가 켜져 있다면 그것도 함께 중지합니다.

  3. RCA, 쿼리 결과, 승인 기록, 복구 전후 지표, 구성 export를 저장합니다. 로그/보고서의 민감 정보를 제거합니다. secrets 없이도 재구성할 수 있는 리소스 이름과 권한 목록을 남깁니다.
  4. Portal → Resource groups → 실습 RG → Overview삭제할 리소스 목록과 태그를 직접 확인합니다. 공유 RG이면 전체 삭제를 하지 말고 자신이 만든 리소스만 선택합니다.

    az group show --name "$RG" --query '{name:name,tags:tags}' -o json
az resource list --resource-group "$RG" --query '[].{name:name,type:type}' -o table
az group delete --name "$RG"

az group show --name "$AGENT_RG" --query '{name:name,tags:tags}' -o json
az resource list --resource-group "$AGENT_RG" --query '[].{name:name,type:type}' -o table
az group delete --name "$AGENT_RG"
    심화 Lab에서 만든 Grafana/VNet/Key Vault/standby RG도 목록 확인 후 정리합니다. Soft-delete와 purge protection이 적용된 Key Vault는 즉시 완전 삭제되지 않을 수 있습니다.
  6. GitHub connector/App 권한과 Key Vault 접근 역할, 로컬 MCP 설정, 워크샵용 action group을 정리합니다. GitHub App을 uninstall/delete할 때 다른 서비스가 쓰는 App인지 확인합니다. 남아 있는 App Service plan과 SRE Agent가 없는지 Portal에서 재확인합니다.
